## Architecture Overview

A Tauri plugin bridges Rust and React. YAML locale files are embedded in the binary at build time and served to the frontend via IPC.

```
┌──────────────────────────────────────────────────────────┐
│                      RUNTIME FLOW                         │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  locales/en.yml  ──include_str!()──►  Embedded in binary │
│  locales/zh-CN.yml                   (via build.rs)      │
│       │                                                  │
│       ▼                                                  │
│  ┌─────────────────────────────────┐                     │
│  │  tauri_plugin_i18n (Rust)       │                     │
│  │  PluginI18n managed state       │                     │
│  │  .translate(key) → Option<&str> │                     │
│  └──────────┬──────────────────────┘                     │
│             │ Tauri IPC                                  │
│             ▼                                            │
│  ┌─────────────────────────────────┐                     │
│  │  @razein97/tauri-plugin-i18n    │                     │
│  │  I18n singleton (JS bridge)     │                     │
│  └──────────┬──────────────────────┘                     │
│             │                                            │
│             ▼                                            │
│  ┌─────────────────────────────────┐                     │
│  │  src/lib/i18n.ts                │                     │
│  │  t(key, params?)                │                     │
│  │  useTranslation()               │                     │
│  │  initI18n()                     │                     │
│  └──────────┬──────────────────────┘                     │
│             │                                            │
│      ┌──────┴──────┐                                     │
│      ▼              ▼                                    │

│  components     modules                                  │
│  (hooks)        (direct t())                             │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Frontend I18N

### Core Library (`src/lib/i18n.ts`)

The entry point for frontend i18n. Exports three items:

| Export | Type | Purpose |
|--------|------|---------|
| `t` | Function | Translation function for non-React use |
| `useTranslation` | React Hook | Returns `{ t, locale, setLocale, availableLocales }` |
| `initI18n` | Async Function | One-time initialization, called on app startup |

**Initialization flow:**
1. `initI18n()` calls `I18n.getInstance().load()` to load translations from the Rust backend
2. Gets the system locale, falls back to store-saved locale
3. Sets `document.documentElement.lang`
4. Subscribes to `i18n:locale_changed` event to react on locale switch
5. Restores any previously-saved user locale preference

### Translation Function (`t`)

```typescript
export function t(key: string, params?: TranslationParams): string
```

- Calls `I18n.getInstance().translate(key)` to look up the translation
- Falls back to returning the raw key if no translation is found
- In DEV mode, logs a console warning when a key resolves to itself (indicating a missing translation)
- Applies interpolation: replaces `{{paramName}}` placeholders with provided values

### React Hook (`useTranslation`)

```typescript
export function useTranslation(): {
  t: (key: string, params?: TranslationParams) => string;
  locale: string;
  setLocale: (newLocale: string) => Promise<void>;
  availableLocales: string[];
}
```

- Reads current locale from Zustand store (reactive via store subscription)
- Fetches available locales from the Rust backend
- `setLocale` persists the change via `I18n.setLocale()` and updates `document.documentElement.lang`

### Usage Patterns

**Pattern A: React components** (use inside component body, after hook)
```tsx
import { useTranslation } from "@/lib/i18n";

export default function MyComponent() {
  const { t } = useTranslation();
  return <Button>{t("common.save")}</Button>;
}
```

**Pattern B: Module scope / non-React** (direct import, called at module load time)
```typescript
import { t } from "@/lib/i18n";

export const insertScript = (editor: BlockNoteEditor) => ({
  title: t("editor.blocks.script.title"),
  onItemClick: () => { /* ... */ },
});
```

**Pattern C: Combined** (both hooks and direct `t` in same file)
```typescript
import { useTranslation, t } from "@/lib/i18n";
```

> When `useTranslation` destructures `t` inside a component, it shadows any module-level `t` import. Don't import both — pick either the hook or the direct function.

### Interpolation

Uses `{{doubleCurlyBraces}}` syntax. Parameters are simple string replacements — no pluralization or formatting logic.

```typescript
t("root.move_items.confirm_question", {
  count: 5,
  itemLabel: "runbooks",
  workspace: "My Workspace",
});
// → "Are you sure you want to move 5 runbooks to the My Workspace workspace?"
```

```yaml
"root.move_items.confirm_question": "Are you sure you want to move {{count}} {{itemLabel}} to the {{workspace}} workspace?"
```

### LLM Tools Window (`src-llmtools/`)

The LLM Tools window (`llmtools.html`) is a separate Tauri window entry point. It shares the **same** i18n infrastructure:

- `src-llmtools/main.tsx` calls `initI18n()` from `../src/lib/i18n` before rendering
- All components import `useTranslation` from `../src/lib/i18n` (aliased to `@/lib/i18n`)
- Uses keys under the `llmtools.*` prefix
- Extraction includes `src-llmtools/**` in the scanner input glob

## Backend I18N (Rust)

### Plugin Setup

**Cargo dependency** (`backend/Cargo.toml`):
```toml
[dependencies.tauri-plugin-i18n]
path = "/tmp/tauri-plugin-i18n"
```

**Build configuration** (`.cargo/config.toml`):
```toml
[env]
TAURI_I18N_PROJECT_DIR = { value = ".", relative = true }
TAURI_I18N_LOCALES_PATH = "locales"
```

These env vars tell the plugin's `build.rs` to embed `locales/*.yml` via `include_str!()` at compile time.

**Plugin initialization** (`backend/src/main.rs`):
```rust
.plugin(tauri_plugin_i18n::init(tauri_plugin_i18n::I18nConfig {
    default_locale: "en".into(),
    ..Default::default()
}))
```

**Locale file bundling** (`backend/tauri.conf.json`):
```json
"bundle": {
  "resources": {
    "../locales/": "locales/"
  }
}
```

**Capability** (`backend/capabilities/migrated.json`):
```json
"permissions": ["i18n:default"]
```

### Translation Methods

**Method 1: Direct `.translate()` call**
```rust
use tauri_plugin_i18n::PluginI18nExt;

let title = app.i18n().translate("llmtools.window.title")
    .unwrap_or("llmtools.window.title");
```

Returns `Option<&str>` — falls back to the raw key if translation is missing.

**Method 2: `tr()` convenience wrapper** (defined in `backend/src/menu.rs`)
```rust
fn tr<R: Runtime>(handle: &AppHandle<R>, key: &'static str) -> String {
    handle.i18n().translate(key).unwrap_or(key).to_string()
}
```

Usage:
```rust
MenuItemBuilder::new(tr(handle, "menu.check_for_updates"))
```

### Files Using I18N

| File | Keys Translated | Method |
|------|----------------|--------|
| `backend/src/menu.rs` | 25 menu item keys | `tr()` wrapper |
| `backend/src/llmtools_window.rs` | 1 window title key | Direct `.translate()` |

All backend i18n is localized to native menu items and window titles. Backend logic (error messages, log output, CLI interactions) is intentionally **not translated** — these are developer/internal-facing.

## Locale Files

### File Structure

```
locales/
├── en.yml       # English (source/default locale, 1269 lines)
└── zh-CN.yml    # Chinese Simplified (1271 lines)
```

Format:
```yaml
_version: 1
"app.name": "Atuin Desktop"

"common.save": "Save"
"common.cancel": "Cancel"

"menu.file": "File"
"menu.edit": "Edit"
```

- `_version: 1` — internal format version
- All values are double-quoted strings
- Keys use dot notation; the separator is `false` in the scanner config, so dots are literal in keys, not namespaces
- Blank lines separate logical groups

### Key Naming Convention

Keys follow a hierarchical dot-notation pattern: `<category>.<subcategory>.<property>`

```
common.save                          — Shared/common UI strings
menu.file                            — Menu bar items
settings.general.ui_scale.label      — Settings with sub-sections
editor.blocks.terminal.title         — Block editor blocks
editor.blocks.terminal.short_desc    — Block descriptions (AI context)
blocks.common.refresh.5s             — Block runtime strings
runbooks.dialog.cancel_execution.title — Runbook management dialogs
workspace.error.folder_unreadable    — Workspace error messages
```

**Rules:**
- Use `common.*` for strings shared across the entire app
- Use `editor.blocks.<type>.*` for block-specific strings
- Use `editor.blocks.group.<name>` for block group/category names
- Use `settings.<section>.*` for settings panel strings
- Use descriptive, hierarchical names — not abbreviations

### Loading Mechanism

The Rust plugin loads locale files in two stages:

1. **Compile time**: The plugin's `build.rs` scans `locales/` and embeds `.yml` files as `&'static str` via `include_str!()`. These ship in the binary.

2. **Runtime** (not used here): If `I18nConfig.runtime_locales_path` were set, additional files would be loaded from disk, merging with or overriding the bundled data.

In memory, the plugin stores a `BTreeMap<locale, BTreeMap<key, value>>`. Lookups are O(log n).

## Extraction Pipeline

### Frontend Collector

**File:** `script/i18n-frontend-collector.cjs`

Uses the **TypeScript compiler API** (not regex) to parse `.ts`/`.tsx` files and find translatable strings.

**What it detects:**

| Detection | How | Example |
|-----------|-----|---------|
| Static `t()` calls | AST: `CallExpression` with string literal argument | `t("common.save")` |
| Static `translate()` calls | Same AST pattern | `translate("menu.file")` |
| `useTranslation().t()` calls | AST: chained call expression | `useTranslation().t("key")` |
| JSX text nodes | All `JsxText` nodes (excluding `<code>`, `<pre>`, `<script>`, `<style>`) | `<p>Hello world</p>` |
| JSX prop strings | Known UI props: `label`, `title`, `placeholder`, `content`, `description`, `tooltip`, `subtext`, `aria-label`, `emptyContent` | `<Input label="Name" />` |
| Object prop strings | Known object keys: `label`, `title`, `content`, `message`, `header`, `placeholder`, `subtext`, `tooltip`, `description`, `emptyContent` | `{ title: "Prometheus" }` |

**Strings the collector skips** via `skipReason()`:
Strings that are not user-facing text:
- Empty strings, single characters
- URLs (`https://...`), file paths, protocol strings (`mailto:`, `atuin:`)
- CSS class lists (`"flex items-center justify-between"`), color values (`#ffeeaa`)
- Shell/code snippets, identifiers (lowercase, no spaces)
- Dot-separated keys (already-i18n keys)
- Strings > 240 characters

**Two modes:**
- **Normal** (`includeSourceLiterals: false`): Only collects `t()`/`translate()` keys. Output: `.i18n-extract/frontend.yml`
- **Audit** (`I18N_AUDIT=1`): Also finds source literals not wrapped in `t()`. Reports potential untranslated strings

### Backend Extractor

**File:** `script/i18n-extract-backend.mjs`

Scans Rust source files (`backend/src/**/*.rs`) with regex for:

| Pattern | Example |
|---------|---------|
| `.translate("...")` | `handle.i18n().translate("menu.file")` |
| `tr("..")` | `tr(handle, "menu.check_for_updates")` |
| `tr_ui("...")` | placeholder for future UI-specific helpers |
| `translate_ui("...")` | placeholder for future UI-specific helpers |

Dynamic (non-literal) calls are logged as warnings for manual review. `.translate()` calls inside the `fn tr` helper itself are skipped.

### Check and Merge Scripts

**File:** `script/i18n-check.mjs`

Compares extraction output against locale files and reports:

- **Missing keys**: found by extraction but not in `en.yml`/`zh-CN.yml`
- **Stale keys**: in locale files but not found by current extraction

The `--write` flag (`bun run i18n:merge`) auto-appends missing keys to both locale files with placeholder values and a comment tag.

### Extraction Commands

```bash
# Extract frontend keys only
bun run i18n:extract:frontend

# Extract backend keys only
bun run i18n:extract:backend

# Extract both
bun run i18n:extract

# Check for missing/stale keys (fails CI if issues found)
bun run i18n:check

# Auto-append missing keys to locale files
bun run i18n:merge

# Full audit (detects source literals not yet wrapped)
I18N_AUDIT=1 bun run i18n:extract:frontend
```

Output goes to `.i18n-extract/` (gitignored).

## What Should NOT Be I18N'd

The following should **never** be wrapped with `t()`:

### Display Names
```typescript
Input.displayName = "Input";     // React DevTools — not user-facing
Table.displayName = "Table";     // React DevTools — not user-facing
```

### Search Aliases
```typescript
aliases: ["prom", "promql", "grafana"],   // Block search keywords
aliases: ["terminal", "run"],              // Not display text
aliases: ["kubectl", "k8s", "pods"],      // Technical commands
```
These are what users type to find blocks — translating them would break searchability.

### Technical Placeholders
```typescript
placeholder="default"           // Internal/default value placeholder
placeholder="current-context"   // kubernetes context placeholder
```

### Numeric Configuration Values
```typescript
{ label: "2", key: "2" },       // Sync concurrency numbers
{ value: 1000 },                 // Millisecond values
```

### Component Gallery Reference Data
The file `src/components/CommandMenu/mock-data.ts` contains ~720 component names and metadata for a UI gallery browser. These are technical reference names, not user-facing product text.

### Test Fixtures
```typescript
// Test assert data — not user-facing
expect(data).toEqual([{ name: "Folder 1", type: "folder" }]);
```

### Auto-generated Bindings
```typescript
// src/rs-bindings/ — TypeScript bindings generated from Rust types
```

### Backend Logic Strings
Error messages in Rust that are logged to console or returned as structured errors (not displayed directly to users in UI). Only user-facing UI strings (menu items, window titles) are translated on the backend.

### Log Output and Console Messages
```typescript
console.debug("[i18n] Missing translation: ...");  // Internal debugging
track_event("runbooks.block.create", { ... });     // Analytics events
```

## Adding New Translations

### Frontend (React/TypeScript)

**Step 1:** Import the translation hook or function:
```typescript
import { useTranslation } from "@/lib/i18n";
// or for non-React modules:
import { t } from "@/lib/i18n";
```

**Step 2:** Use the translation:
```tsx
// In a React component:
const { t } = useTranslation();
<Button>{t("common.save")}</Button>

// With interpolation:
<p>{t("workspace_tree.count.runbook_many", { count: items.length })}</p>
```

**Step 3:** Add the key to `locales/en.yml`:
```yaml
"common.save": "Save"
```

**Step 4:** Add the corresponding entry to `locales/zh-CN.yml`:
```yaml
"common.save": "保存"
```

**Step 5:** Run extraction to verify:
```bash
bun run i18n:extract
bun run i18n:check
```

### Frontend (Non-React Modules)

For block spec registrations, state management, and utility modules that exist at module scope:

```typescript
import { t } from "@/lib/i18n";

export const insertScript = (editor: BlockNoteEditor) => ({
  title: t("editor.blocks.script.title"),
  group: t("editor.blocks.group.execute"),
  onItemClick: () => { /* ... */ },
});
```

> `t()` at module scope evaluates once at load time. The app must be restarted for locale changes to apply to these strings.

### Backend (Rust)

**For menu items:**
```rust
// In backend/src/menu.rs
use tauri_plugin_i18n::PluginI18nExt;

fn tr<R: Runtime>(handle: &AppHandle<R>, key: &'static str) -> String {
    handle.i18n().translate(key).unwrap_or(key).to_string()
}

// Usage:
MenuItemBuilder::new(tr(handle, "menu.new_item"))
```

**For other Tauri windows/titles:**
```rust
use tauri_plugin_i18n::PluginI18nExt;

let title = app.i18n().translate("my_window.title")
    .unwrap_or("my_window.title");
```

**Step 3:** Add the key to both `locales/en.yml` and `locales/zh-CN.yml`.

**Step 4:** Run backend extraction:
```bash
bun run i18n:extract:backend
```

### HTML Templates

HTML files like `llmtools.html` use static `<title>` tags. The window title can be set via the Tauri Rust backend using `.translate()`:

```rust
// backend/src/my_window.rs
let title = app.i18n().translate("my_window.title")
    .unwrap_or("Default Title");
```

The static `<title>` in the HTML serves as a fallback when the Tauri window title has not yet been set.

## Adding a New Locale

**Step 1:** Copy the English locale file:
```bash
cp locales/en.yml locales/fr.yml
```

**Step 2:** Translate all values in `fr.yml`. Keep the keys identical — only translate the right-hand values.

**Step 3:** The new locale will be automatically detected by `tauri_plugin_i18n` at compile time (the build.rs scans all files in `locales/`).

**Step 4:** If you need to expose the locale in the UI language selector, add it to the available locales list in your language selection component.

**Step 5:** Verify:
```bash
bun run i18n:check
```

## Maintenance Procedures

### Auditing for Missing Translations

Run the source-literal audit to find strings in the codebase that are user-facing but not yet wrapped in `t()`:

```bash
I18N_AUDIT=1 bun run i18n:extract:frontend
```

This will output:
- **Included source literals** — strings that look translatable but are not yet wrapped
- **Skipped source literals** — strings correctly excluded (URLs, code, identifiers, etc.)
- **Dynamic translation warnings** — `t(variableExpression)` calls that need manual review

### Cleaning Stale Keys

Run the check script to find keys that exist in locale files but are no longer referenced in source code:

```bash
bun run i18n:check
```

If it reports stale keys, manually remove them from both `en.yml` and `zh-CN.yml`.

### Checking Extraction Coverage

After adding new translations:
```bash
bun run i18n:extract    # Regenerate extraction output
bun run i18n:check      # Verify no missing/stale keys
```

The check script exits with code 1 if issues are found, making it suitable for CI:
```yaml
# GitHub Actions example
- name: Check i18n
  run: bun run i18n:check
```

## Known Patterns and Anti-Patterns

### Correct Patterns

```tsx
// ✓ React component with useTranslation hook
const { t } = useTranslation();
<Button>{t("common.save")}</Button>

// ✓ Non-React module with direct t import
import { t } from "@/lib/i18n";

// ✓ Interpolation with named params
t("notifications.duration.seconds", { seconds: 30 })

// ✓ Block spec with t() at module scope
export const insertFoo = (editor) => ({
  title: t("editor.blocks.foo.title"),
  group: t("editor.blocks.group.database"),
})

// ✓ Using existing common keys
t("common.untitled")
t("common.personal")
t("common.delete")
```

### Anti-Patterns

```tsx
// ✗ Importing t when useTranslation already provides it
import { useTranslation, t } from "@/lib/i18n";  // t is unused/shadowed
const { t } = useTranslation();  // shadows the import

// ✗ Translating React displayName
MyComponent.displayName = t("something");  // displayName is dev-only

// ✗ Translating block aliases
aliases: [t("prom"), t("promql")],  // aliases are search keywords, not display text

// ✗ Translating numeric values
{ label: t("2") }  // numbers are universal

// ✗ Dynamic key construction (not statically extractable)
t(`editor.blocks.${type}.title`)  // use a static key instead

// ✗ Using t() before initI18n() has completed
const title = t("app.name");  // may not be loaded yet
```

### Edge Cases

**Module-scope `t()` and locale switching**: `t()` at module scope (block specs, constants) evaluates once on load. The user must restart the app for locale changes to apply. For reactive translations, move the `t()` call inside a React component.

**Missing translation fallback**: `t()` returns the key itself when no translation is found. In DEV mode this logs a warning. Run `bun run i18n:check` to verify keys exist.
